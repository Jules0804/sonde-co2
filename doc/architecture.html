Décorticage de la version production (firmware ESP-IDF architecturé) : un noyau de décision pur et testable, mais pas encore la machine qui l'exécute. Un prototype Arduino fonctionnel (wifi_ap_web) existe en parallèle — comparaison dans analyse-proto.md.

01Vocation

Un capteur SCD41 mesure le CO₂ ambiant ; un cœur de régulation PI en déduit un taux d'ouverture de ventilation (0–100 %) pour tenir une cible (défaut 1000 ppm) ; un DAC DFR0971 (sortie 0–10 V) commande le variateur. Une interface web locale (PWA sur point d'accès Wi-Fi), à rôles, permet configuration et supervision. Mode service par appui long, historique et journal d'événements persistés en flash.

02Architecture en couches

Un « ports & adapters » fait à la main : le noyau calcule quoi faire (trames, actions, plans, JSON) sans jamais toucher au matériel ; un fin shell d'adaptateurs exécute l'I/O réelle. C'est ce qui rend le noyau testable sur PC.

04Principe de sûreté

FAIL → 100 %
L'état sûr est la ventilation à plein débit. Au démarrage, sur défaut capteur, sur CO₂ trop haut, sur échec d'écriture I²C, ou tant que le matériel n'est pas validé, la sortie est forcée à 100 %. Ce repli est câblé dans presque chaque branche des machines à états — c'est la propriété à préserver coûte que coûte lors de la refonte.

06Défauts concrets relevés

NE COMPILE PAS
lot1_drivers.cpp:66 — I2cWrite::bytes (array<8>) initialisé depuis frame.bytes (array<4>). Interdit en C++ standard.
INCOHÉRENCE
Adresse I²C du DAC : 0x58 dans le code vs 0x5F dans le test matériel.
DONNÉES
Compteurs boot_id / séquences non persistés (repartent de 0) ; epoch_seconds toujours 0 → historique sans datation.
COUPLAGE
La couche « matériel » (sensor_cycle, actuator_output) dépend de la couche « contrôle » — dépendance à inverser.
